Abertura · Introdução & Motivação
Por que mais um ORM?

O problema é antigo

Classes, identidade e herança de um lado; tabelas e chaves, sem noção de herança, do outro (Fowler).

ORMs como mediação

Hibernate (2001) populariza o mapeamento no Java e inspira o padrão JPA. O padrão se difunde por todas as linguagens de uso corrente.

Ecossistema TypeScript

Tipagem estática torna entidades e consultas verificáveis pelo compilador — TypeORM, Prisma e Drizzle formam um campo maduro.

A lacuna
O Prisma, ORM dominante, não tem herança de tabela única (STI) nativa. O TypeORM é o mais próximo do ideal, mas limitado no tratamento de consultas. Nenhum reúne as duas qualidades.
A proposta
Unir modelagem rica e composição de consultas adequada, modernizando a base: decorators padronizados (Stage-3) e o runtime Bun.

Os conceitos que estruturam o trabalho
01

Decorators

Forma de metaprogramação em TypeScript, paralela às anotações Java. Proposta TC39 em Stage-3 — o TypeORM ainda usa o dialeto legado, com polyfill.

@Entity(database)
class User { }
02

Anti-padrão N+1

Uma consulta que retorna N resultados, seguida de N consultas. Prolifera porque iterar coleções é natural em OO e o ORM oculta o custo (Reformulator, ASE '22).

pedidos // 1 consulta
for(p of pedidos) { p.cliente } // +N consultas
03

Data Mapper × Active Record

No Active Record, o objeto encapsula linha, acesso e domínio. No Data Mapper, uma camada à parte mantém objetos e banco mutuamente alheios (Fowler).

user.save()
repo.save(user)
04

Query builder type-safe

Interface fluente que constrói a consulta programaticamente. O ponto decisivo: ser integralmente verificada pelo sistema de tipos (Gil & Lenz).

✗ query("SELECT … WHERE name = '…'")
✓ users.where(name).equals("Ana")
05

Herança de tabela única (STI)

Toda a hierarquia em uma tabela, com coluna discriminadora. A estratégia mais rápida na leitura — nunca recorre a junções (OpenJPA).

class Admin extends User
→ users(id, discriminator, name, department)

Materiais e métodos · Mapeamento por decorators
A classe é a fonte da verdade do esquema
Duas entidades e a relação entre elas — a declaração é registrada quando a classe é definida e consumida pelo ORM em tempo de execução.
@Entity(database)
class User {
  @PrimaryColumn({
    type: COLUMN_TYPE.TEXT,
    autogeneration: { clientSide: () => randomUUID() },
  })
  id?: PrimaryKey<string>;

  @Column({ type: COLUMN_TYPE.TEXT })
  @NotNullable
  name!: string;

  @ToOne({ target: () => Profile })
  @Nullable
  profile?: Profile;
}
@Entity(database)
class Profile {
  @PrimaryColumn({
    type: COLUMN_TYPE.SERIAL,
    autogeneration: { dbSide: () => undefined },
  })
  id?: PrimaryKey<number>;

  @Column({ type: COLUMN_TYPE.TEXT })
  @NotNullable
  bio!: string;
}

Registro em um banco específico

Registra a classe como entidade mapeada do banco passado como argumento — a metadata vive por banco, sem estado global nem polyfill.

Declarado na definição, consumido na execução

A declaração é registrada quando a classe é definida e consumida pelo ORM em tempo de execução — é aqui que a metaprogramação por decorators acontece.

Materiais e métodos · Decorators · 2 / 4
@PrimaryColumn — chave primária e geração do valor
// User: valor gerado pela aplicação
@PrimaryColumn({
  type: COLUMN_TYPE.TEXT,
  autogeneration: { clientSide: () => randomUUID() },
})
id?: PrimaryKey<string>;

// Profile: valor gerado pelo banco
@PrimaryColumn({
  type: COLUMN_TYPE.SERIAL,
  autogeneration: { dbSide: () => undefined },
})
id?: PrimaryKey<number>;

Declara a chave primária

Com seu tipo de coluna e a forma de geração do valor.

Dois lados de geração

clientSide — identificador produzido pela aplicação antes da inserção (UUID). dbSide — o próprio PostgreSQL preenche (coluna SERIAL).

Reflexo no nível de tipos

A anotação PrimaryKey<...> marca, no sistema de tipos, o que é chave — exigível pelo compilador nas operações de persistência.

Materiais e métodos · Decorators · 3 / 4
@Column + @NotNullable + @Nullable — colunas e restrições
// coluna obrigatória
@Column({ type: COLUMN_TYPE.TEXT })
@NotNullable
name!: string;

// coluna opcional
@Column({ type: COLUMN_TYPE.TEXT })
@Nullable
nickname?: string;

@Column

Marca um campo da classe como coluna comum da tabela, com seu tipo.

@NotNullable

Impõe a restrição NOT NULL à coluna no banco.

@Nullable

Torna a coluna opcional — a linha pode existir sem valor no campo, que admite nulo no banco.

Espelho no nível de tipos

Os modificadores ? e ! indicam, para o compilador, o que é opcional ou obrigatório — a mesma informação nos dois níveis.

Materiais e métodos · Decorators · 4 / 4
@ToOne + @ToMany — relações entre entidades
// para-um: User → Profile
@ToOne({ target: () => Profile })
@Nullable
profile?: Profile;

// para-muitos: Group → User
@ToMany({ target: () => User })
@Nullable
users?: User[];

@ToOne

Estabelece uma relação para-um com outra entidade, indicada por uma função que devolve a classe-alvo.

@ToMany

O lado para-muitos da associação: o campo é uma coleção da entidade-alvo.

O que vira no banco

Uma coluna de chave estrangeira (profile_id) na tabela users. O lado para-muitos não cria coluna — é lido pela mesma chave.

Materiais e métodos · Herança de entidades
STI — a herança do código preservada no banco
@Entity(database)
class Admin extends User {
  @Column({ type: COLUMN_TYPE.TEXT })
  @NotNullable
  department!: string;
}

Reconhecida automaticamente

Nenhum decorator de configuração de herança — basta persistir duas classes da mesma hierarquia.

Uma tabela, uma coluna discriminadora

User e Admin acomodados na mesma tabela; a coluna discriminator guarda o subtipo de cada linha.

Leitura sem junção

Colunas próprias do subtipo admitem nulo nas demais linhas; recuperar uma instância nunca exige junções.

Materiais e métodos · Persistência e consultas
Consultas com Query Builder type-safe
const result = await orderRepo.findMany({
  where: (o) => [
    o.status.in(['paid', 'shipped']), // status IN (…)
    o.totalCents.gte(10_000), // total >= R$ 100,00
    o.totalCents.lt(1_000_000), // total < R$ 10.000,00
    o.priority.ne('low'), // prioridade != 'low'
    o.canceledAt.isNull(), // não cancelado
  ],
});

O repositório é a entrada

Interface semelhante a uma coleção (Fowler, p. 309). Cada acesso ao banco fica visível e explícito — ataca o N+1 apresentado na revisão.

Predicados sobre os campos da entidade

A consulta é composta por encadeamento de operações (in, gte, lt, ne, isNull) — sem SQL em texto.

Verificada em compilação

Campos e operações são tipados a partir da declaração da entidade: referir campo inexistente é rejeitado pelo compilador.

Traduzida para SQL parametrizado

A tradução final produz SQL sempre parametrizado via driver SQL do Bun — nunca concatenação de strings.
